## 1. 为什么放到 v2

v1 的目标是验证数据模型、事件语义与单服体验；外部模式与分布式层解决的是另外三个问题：

- 多台 BDS 汇聚到一个面板；
- Web 服务独立扩容/独立重启；
- 长期归档与跨服查询。

这些问题不改变“背包/物品去向/命令”的核心模型，但会引入新的失败模式（推送丢失、乱序、重复、跨服时钟、租户隔离）。在单服语义没有跑稳之前做这些，会把不确定性叠加在一起。

v2 的进入条件：

1. v1 的运行时探针全部有结论，影子状态/备份/物品去向在真实服上稳定运行 ≥ 2 周；
2. v1 的模块 API 与数据 schema 没有破坏性变更；
3. 有明确的多服需求与运维资源（独立 Web 进程、数据库、消息队列）。

## 2. 外部模式

### 2.1 拓扑

```
BDS 进程                         独立进程 / 容器
  WebBundle qjs 插件  ──HTTP/WS──▶  webbundle-web
       │                              ├─ 页面与 API
       └─ 本地存储（形态 A）          ├─ SQLite / RocksDB / MongoDB
                                       ├─ Redis（可选）
                                       └─ Kafka（可选）
```

插件不启动页面服务，只把备份、增量、物品去向事件、命令结果推送到 `webbundle-web`；命令由插件轮询或通过 `WSClient` 接收。

### 2.2 与 v1 的关系

- 复用 v1 的 `/api/v1` 契约、动作描述、错误码、前端 `dist/`。
- 外部服务增加多服聚合、WebSocket/SSE、中心库与长期归档。
- 插件侧只增加 `push` 适配器与命令拉取；核心领域逻辑不变。

### 2.3 模式对照

| 能力 | v1 embedded | v2 external | v2 hybrid |
|---|---|---|---|
| 额外进程 | 可选 `webbundle-web` | 中心 `webbundle-web` | 两者 |
| 网页 | 内置/单独挂载 | 中心网页 | 两者 |
| 多服聚合 | 无 | 有 | 有 |
| 实时方式 | 1s 轮询 | WebSocket/SSE | 本服轮询 + 中心推送 |
| 历史深度 | 本地 RocksDB | 中心库全量 | 两者 |
| 适用规模 | 单服 ≤ 500 在线 | 多节点 | 多节点 + 本服兜底 |

### 2.4 外部 Web 部署

1. 部署 `webbundle-web`（推荐 Rust/axum；也可用任意实现满足契约）。
2. 默认 SQLite（单机）或 MongoDB（多机）。
3. 配置示例：

```json
{
  "listen": "127.0.0.1:8080",
  "publicUrl": "https://panel.example.com",
  "db": { "driver": "sqlite", "path": "./data/webbundle.db" },
  "auth": { "tokens": [] },
  "push": { "tokens": [] },
  "cors": { "allowOrigins": ["https://panel.example.com"] }
}
```

4. 反向代理终止 TLS；不要把 19380/19381 直接暴露公网。
5. BDS 配置：

```json
"mode": "external",
"web": { "enabled": false },
"push": {
  "url": "https://panel.example.com",
  "token": "<与 webbundle-web push.tokens 对应>"
}
```

6. 在面板确认服务器上线、备份与物品去向事件到达；提交一条 `say` 命令验证回路。

## 3. 推送契约

插件 → 外部服务：

### 3.1 注册与心跳

```http
POST /push/v1/register
Authorization: Bearer <pushToken>

{
  "serverId": "srv-1",
  "serverName": "生存一区",
  "pluginVersion": "0.1.0",
  "bdsVersion": "1.26.40",
  "capabilities": ["snapshot", "flow", "command", "audit"],
  "lastAckSeq": 0
}
```

```http
POST /push/v1/heartbeat
{ "serverId": "srv-1", "ts": 1730000000000, "queueDepth": 12, "lastAckSeq": 1024 }
```

### 3.2 备份与事件

```http
POST /push/v1/snapshots
{
  "serverId": "srv-1",
  "items": [ { "...": "InventorySnapshot" } ]
}
```

```http
POST /push/v1/flow
{
  "serverId": "srv-1",
  "items": [ { "...": "FlowEvent" } ]
}
```

```http
POST /push/v1/audit
{ "serverId": "srv-1", "items": [ { "...": "AuditRecord" } ] }
```

响应：

```json
{ "ok": true, "data": { "accepted": 200, "duplicates": 0, "lastAckSeq": 1224 } }
```

- 批次上限：200 条或 64KB；超过拆批。
- 服务端按 `id`/`eventId` 幂等；重复返回 `duplicates` 计数。
- 失败返回 4xx/5xx；4xx 不重试（除非 408/429），5xx 退避重试。

### 3.3 命令

```http
GET /push/v1/commands?serverId=srv-1&status=queued&limit=8
```

```json
{
  "ok": true,
  "data": [
    { "taskId": "01J...", "command": "say hello", "operator": "admin", "createdAt": 1730000000000 }
  ]
}
```

```http
POST /push/v1/command-result
{ "serverId": "srv-1", "taskId": "01J...", "state": "succeeded", "result": { "success": true, "output": "..." } }
```

- 插件默认 1 秒轮询；支持 WebSocket 时由外部服务推送 `command.queued`。
- 外部服务不能直接执行命令；它只排队，执行权在插件。

### 3.4 安全

- `pushToken` 与 Web 令牌分离；只允许 `/push/v1/*`。
- 强制 HTTPS；插件侧校验证书（配置 `allowInsecure` 仅供本机调试）。
- 请求带 `X-WebBundle-Server` 与 `X-WebBundle-Seq`；服务端校验 `serverId` 与令牌绑定。
- 重放保护：`ts` 与 `lastAckSeq` 单调；服务端拒绝明显过期/重复批次。
- 推送失败进入本地 spool；spool 有容量上限，超限丢弃最旧并告警。

## 4. 实时通道

### 4.1 WebSocket

```http
POST /api/v1/stream/ticket
Authorization: Bearer <token>

{ "ok": true, "data": { "ticket": "one-time...", "expiresAt": 1730000030000 } }
```

```text
GET /api/v1/stream/ws?ticket=one-time...
→ { "type": "subscribe", "channels": ["inventory:2535...", "flow"] }
← { "type": "inventory.delta", "xuid": "2535...", "seq": 1026, ... }
← { "type": "flow.recorded", "event": { ... } }
← { "type": "ping", "ts": 1730000000000 }
```

- 浏览器 WebSocket 不能设置 `Authorization` 头，因此用一次性 ticket；30 秒有效、单次使用、绑定令牌与 IP。
- 订阅按权限过滤；无权限的频道返回 `error`。
- 服务端每 30 秒 ping；客户端 60 秒无消息重连。
- 断线重连后从最后 `seq` 补拉；补不上则全量刷新。
- 轮询接口仍保留作为降级。

### 4.2 SSE（可选）

如果外部服务不想维护 WebSocket，可用 SSE：`GET /api/v1/stream/sse?ticket=...`，事件格式与轮询一致。SSE 只支持单向推送，命令仍走 POST。

## 5. 分布式存储

v1 只有进程内热缓存 + 本地 RocksDB/LevelDB。v2 增加：

| 层 | 实现 | 用途 |
|---|---|---|
| 热层 | Redis Hash | 多节点共享在线背包；TTL 极短 |
| 温层 L2 | MongoDB / Cassandra / Spanner | 多服共享历史，按 `serverId + xuid` 分区 |
| 日志层 | Kafka + 冷归档 | 物品流转事件流；Parquet/Iceberg |

### 5.1 Redis 热层

Key：

```
webbundle:hot:<serverId>:<xuid>   Hash
  seq, ts, name, dim, pos, hash
  inv / armor / offhand / ender  紧凑数组
```

- TTL 120 秒；更新刷新；离线删除。
- 目标体积 ≤ 8KB；超过时只保留 `hash` 与 `ref`，客户端回源温层。
- listpack 阈值建议：`hash-max-listpack-entries 128`、`hash-max-listpack-value 64`。
- 发布订阅 `webbundle:hot` 只带 `xuid` 与 `seq`，详情回查。
- Redis 不可用时绕过，单机继续。

### 5.2 MongoDB

```js
// collection: snapshots
{
  _id: "srv-1:2535...:1024",
  serverId: "srv-1",
  xuid: "2535...",
  seq: 1024,
  ts: 1730000000000,
  minute: 28833333,
  hash: "9a3c...",
  payload: BinData(0, "<zstd protobuf>"),
  schema: 1
}
```

索引：

```js
db.snapshots.createIndex({ serverId: 1, xuid: 1, ts: -1 });
db.snapshots.createIndex({ serverId: 1, minute: 1 }, { unique: true });
db.flow.createIndex({ serverId: 1, xuid: 1, ts: -1 });
db.flow.createIndex({ serverId: 1, itemKey: 1, ts: -1 });
```

### 5.3 Cassandra / Spanner

```sql
CREATE TABLE snapshots (
  server_id text,
  xuid text,
  ts bigint,
  seq bigint,
  minute bigint,
  hash text,
  payload blob,
  schema int,
  PRIMARY KEY ((server_id, xuid), ts, seq)
) WITH CLUSTERING ORDER BY (ts DESC, seq DESC)
  AND compression = {'sstable_compression': 'ZstdCompressor'};
```

- 分区键 `(serverId, xuid)`，同一玩家顺序写。
- 大字段放 `payload`；查询必须带分区键或时间范围。

### 5.4 Kafka

| Topic | Key | 分区 | 保留 | 压缩 |
|---|---|---|---|---|
| `webbundle.snapshot.v1` | `xuid` | 12 | 7d | ZSTD |
| `webbundle.flow.v1` | `xuid` | 12 | 30d | ZSTD |
| `webbundle.command.v1` | `taskId` | 6 | 30d | LZ4 |
| `webbundle.audit.v1` | `serverId` | 6 | 180d | ZSTD |

Producer：

```properties
acks=all
enable.idempotence=true
compression.type=zstd
linger.ms=50
batch.size=65536
max.in.flight.requests.per.connection=5
```

- Key 用 `xuid`，同一玩家分区有序。
- `eventId` 幂等；消费者去重。
- Kafka 不可用时写本地 spool，恢复后按序补发；spool 上限默认 512MB。

### 5.5 冷归档

```
s3://<bucket>/webbundle/
  flow/dt=2026-10-19/hour=13/part-0001.parquet
  snapshot/dt=2026-10-19/hour=13/part-0001.parquet
  audit/dt=2026-10-19/part-0001.parquet
```

- Parquet + ZSTD；按日期/小时分区。
- Kafka Connect S3 Sink 或归档任务生成；可选 Iceberg/Glue。
- 先写临时目录，成功后原子重命名；默认保留 180 天。

## 6. 多服聚合与租户

- 所有中心查询必须带 `serverId` 过滤；跨服 ID 猜测返回 403/404。
- 单租户多服：一个面板管理多台 BDS；`serverId` 是隔离键。
- 多租户：`tenantId + serverId`；令牌绑定租户；数据库行/索引带 `tenantId`；禁止跨租户聚合。
- 事件顺序：每服单调 `seq` + `serverId`；墙钟仅展示，不用于仲裁。
- 多服恢复：只允许恢复目标服务器在线玩家；跨服恢复默认禁止。

## 7. 从 v1 迁移

1. v1 数据（RocksDB/LevelDB）作为本服历史保留；不强制导入中心库。
2. 中心库从 v2 上线时刻开始接收新事件；旧数据按需导入（离线工具）。
3. 页面从 v1 单独挂载 `webbundle-web` 切到中心 `webbundle-web`：同一份 `dist/`，改 `/boot.js` 的 `apiBase`；v1 的独立网页端可保留作为冷查看兜底。
4. 命令入口不变：v2 只是把动作队列放到中心，执行仍在插件。
5. 回滚：保留 v1 的内置网页与独立 `webbundle-web`；关闭中心 push 即回到 v1。

## 9. 不要提前做的事

- 不要在 v1 代码里预留 `push` 抽象、Redis 适配器、Kafka producer 的“空壳”；等 v2 需要时再加，避免 v1 被未使用的抽象拖慢。
- 不要在 v1 的模块 API 里暴露多服/租户字段；v1 单服模型更简单。
- 不要把 v2 的部署复杂度写进 v1 的安装文档；v1 用户只需要 BDS + 插件，离线查看再部署 `webbundle-web`。
