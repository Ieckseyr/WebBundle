## 1. 当前形态

```text
形态 A：插件内置网页
  BDS + WebBundle 插件 + LSE HttpServer
  http://服务器地址:19380/

形态 B：独立网页端
  BDS ──HTTP 推送──▶ webbundle-web（Node.js）
  http://服务器地址:8080/
```

两种形态都通过普通 HTTP 对外提供服务。BDS 停止后：

- 形态 A 不可用
- 形态 B 仍可查看最后一次同步的数据
- 形态 B 的写入动作会排队，等待 BDS 恢复后执行

## 3. 备份模型

### 3.1 单份快照

每份快照包含：

- `id`
- `xuid` / `name` / `uuid`
- `seq`
- `ts`
- `reason`
- `batchId` / `batchAt` / `batchReason`
- `itemCount`
- `containerCounts`
- `inventory` / `armor` / `offhand` / `ender`
- `nbtRef` 引用

本地快照不重复保存 `nbtRefs` 全文。大 NBT 存为：

```text
nbt:<hash>
```

只有外部推送副本会附带 `nbtRefs`。

### 3.2 备份批次

`batchId` 是“备份文件夹”的依据：

| 场景 | 批次行为 |
| --- | --- |
| 分钟备份 | 同一分钟所有在线玩家共享一个 batch |
| 手动全服备份 | 所有在线玩家共享一个 batch |
| 关服备份 | 所有在线玩家共享一个 batch |
| 单玩家手动备份 | 独立 batch |
| 进服/退服 | 各自独立 batch |
| 离线快照 | 独立 batch |

旧快照没有 `batchId` 时，前端按以下规则兼容分组：

- 分钟备份：按 `minute`
- 其他备份：按理由 + 5 秒窗口

旧快照可能没有 `containerCounts`，此时文件夹只显示总物品数。

### 3.3 全服备份页

- 以备份时间/批次为主，显示为文件夹
- 展开后显示：
  - 玩家名 / XUID
  - 该玩家备份时间
  - 物品总数
  - 背包 / 装备 / 副手 / 末影箱槽位数量
  - 查看
  - 还原

### 3.4 玩家备份侧边栏

查包页右上角「备份历史」打开右侧抽屉：

- 个人 / 事件备份
- 系统分钟备份中该玩家的备份

### 3.5 快照查看与修改

快照查看模式为**只读**：

- 可以查看完整背包和物品
- 不能直接修改快照
- 点击「还原此备份」写回玩家
- 还原后自动回到实时背包，可继续用物品编辑器修改

这是为了避免在查看历史备份时误写实时玩家数据。

## 4. 认证与部署

### 4.1 监听

```json
"web": {
  "host": "0.0.0.0",
  "port": 19380
}
```

```json
"listen": "0.0.0.0:8080"
```

对外访问：

```text
http://服务器IP:19380/
http://服务器IP:8080/
```

`127.0.0.1` 只用于服务器内部：

- `bdsUrl`
- `external.url` 推送
- 本机启动脚本

### 4.2 首次管理员

- 首次创建管理员必须输入 BDS `config.json` 的 `web.token`
- 本机、面板服、独立端都不例外
- 不接受 `external.token` / `pushToken`
- 独立端会调用 BDS `/api/v1/meta` 验证该 Token

### 4.3 Cookie

```text
HttpOnly
SameSite=Strict
Path=/
Max-Age=43200
```

纯 HTTP 不设置 `Secure`。只有反向代理传入：

```text
X-Forwarded-Proto: https
```

才设置 `Secure`。

### 4.4 非安全上下文的登录

手机通过 `http://192.168.x.x` 访问时通常没有 `crypto.subtle`。

处理顺序：

1. WebCrypto PBKDF2
2. WebCrypto 不可用或调用失败
3. 纯 JS `web/pbkdf2.js`
4. 都没有才报错

纯 JS 后备：

- PBKDF2-HMAC-SHA256
- 210000 次迭代
- 每 5000 次让出事件循环
- 按钮显示「验证中 xx%」

### 4.5 内置静态资源

BDS 内置网页使用白名单：

```js
["index.html", "app.js", "app.css", "style.css", "pbkdf2.js", "textures/items-map.json"]
```

新增静态文件必须加入白名单，否则会被 SPA 兜底为 `index.html`。

## 5. 性能与存储

### 5.1 已做

- `/overview` 3 秒缓存
- 审计校验 10 秒缓存，显式校验强制刷新
- 快照热力/数量 30 秒缓存
- 合成检测 30 秒兜底轮询
- 合成缓存 + `onInventoryChange` 事件检查
- `onJoin` 立即初始化合成缓存
- shadow 每分钟遍历在线玩家，并按同一 batch 采集
- 动作 tick 每次最多执行 4 个任务
- external spool 在途锁 + 指数退避
- flow、玩家、快照索引分页：
  - 每页 200 条
  - 每次只写当前页和页目录

### 5.2 存储索引现状

| 索引 | 状态 |
| --- | --- |
| `flow:index` | 分页 |
| `player:index` | 分页 |
| `idx:<xuid>` | 分页 |
| `task:index` | 仍是全量数组 |
| `audit:index` | 仍是全量数组 |

### 5.3 外部推送

- 普通事件失败进入 spool
- heartbeat/register/shutdown 不入 spool
- spool 每批 10 条
- 失败批次回填
- 指数退避，最长 60 秒
- 成功清零

## 6. 已知限制

### 6.1 待实现

| 项目 | 说明 |
| --- | --- |
| 多账号权限组 UI | 目前只有单管理员账号和角色等级，没有账号列表/分发/分组管理 |
| 扩展页面级权限 | 扩展页只要求 `inventory.read`，不能按页面细化 |
| 快照直接编辑 | 设计为只读查看，必须还原后编辑实时背包 |
| 真正的系统级备份事务 | `batchId` 已能表达批次，但一次批次写入没有跨玩家原子事务；中途失败会留下部分玩家 |
| 预览页复用 | `preview.html` / `preview.js` 仍是独立硬编码实现 |
| 前后端 `app.js` 重命名 | 仍靠目录区分 |

### 6.2 部分实现

| 项目 | 缺口 |
| --- | --- |
| shadow 实时同步 | offhand/ender 仍依赖操作后 `setSlot`，不是完整实时事件 |
| shadow delta 去重 | `setSlot` 与 `onInventoryChange` 可能产生重复增量 |
| 三套认证模式 | 内置登录、独立登录、Bearer Token 仍并存；页面已尽量统一 |
| `/overview` flow | 仍查询最多 500 条 flow，只做了缓存，未做增量统计 |
| 审计缓存 | `/overview` 可能使用最多 10 秒旧结果；`/audit/verify` 强制刷新 |
| 旧快照兼容 | 缺 `batchId` / `containerCounts` / 可能含 `nbtRefs` 全文 |
| 公网反向代理 | `external.publicUrl` 未配置时，独立网页链接按当前浏览器主机名推导 |
| PBKDF2 手机性能 | 纯 JS 210000 次迭代可能需数秒，取决于手机性能 |

### 6.3 保持设计

| 项目 | 原因 |
| --- | --- |
| 潜影盒内容只读 | 直接改嵌套容器会破坏容器状态 |
| 快照查看只读 | 避免误写实时玩家 |
| 插件不导出物品写 API | 外部插件只能注册页面/模块，不能直接改背包 |
| 不用外部 npm 依赖 | BDS QuickJS 与独立端都保持零依赖 |
| 单服 | 多服聚合仍属于 v2 规划 |

### 6.4 公网 HTTP 风险

代码已监听 `0.0.0.0`，但 HTTP 明文会暴露登录密码和 Cookie。

公网部署至少需要：

- 防火墙放行 `19380` / `8080`
- 云安全组放行
- NAT / 端口映射
- 反向代理启用 HTTPS
- 保留 `Host` 与 `X-Forwarded-Proto`

## 10. 结论

当前版本满足：

- 单服背包查看/修改
- 在线/离线快照
- 全服备份文件夹
- 玩家侧边栏备份
- 还原与审计
- 内置/独立两种 HTTP 部署
- 无 WebCrypto 的 HTTP 登录

仍需重点投入的方向：

1. 多账号与权限组
2. shadow offhand/ender 完整实时同步
3. 系统级备份事务
4. 旧快照迁移
5. 反向代理/HTTPS 部署收口
6. 前端重复代码清理
