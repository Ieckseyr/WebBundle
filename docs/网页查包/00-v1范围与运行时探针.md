# v1 范围与运行时探针

> 状态：v1.3（按“离线查看属于单独挂载网页端”修正）
> 上游：[README](README.md) / [总体架构](01-总体架构与设计决策.md) / [单独挂载网页端](07-单独挂载网页端与离线修改.md)
> 本文回答两个问题：**v1 到底做什么**，以及**在写模块宿主之前必须先验证什么**。

---

## 1. 先把边界说清

**BDS 离线查看不是插件内置能力。** 它是**单独挂载的网页端**的功能：

- 插件内置网页（qjs `HttpServer`）只在 BDS 运行时可用；BDS 一停，它就不存在。
- 单独挂载的网页端（`webbundle-web`，独立进程/独立部署）自己有数据库，接收插件推送的数据；BDS 停止后它仍可展示最后一次备份。
- **如果没有单独挂载这个网页端，BDS 离线查看就完全不可用**，没有内置兜底，也不假装可用。
- 单独挂载网页端可以部署在本机，也可以部署在另一台机器；它是独立组件，不是插件进程的一部分。

这个边界决定了 v1 的两套形态：

```
形态 A：插件内置网页（embedded）
  BDS + qjs 插件 + LSE HttpServer
  只在 BDS 运行时可用；没有离线查看。

形态 B：单独挂载网页端（external）
  BDS + qjs 插件 ──推送──▶ webbundle-web（独立进程/独立库）
  BDS 停止后，webbundle-web 仍可查看最后一次备份。
  未部署 webbundle-web = 没有离线查看。
```

评审曾指出“v1 范围像 v3”。这里继续收敛：v1 的核心是**形态 A 可用 + 形态 B 可选**；形态 B 是离线查看的唯一来源，没有它就没有冷查看。分布式/多服/Redis/Mongo/Kafka/WebSocket 仍在 v2（06）。

新增需求：

- 查看物品**完整 NBT**；
- 修改玩家背包、修改背包内物品 NBT、还原历史背包；
- 支持修改**离线玩家**背包（BDS 运行时通过 LSE NBT API；BDS 关闭时由单独挂载网页端排队，开服后执行）。

## 2. v1 范围

### 2.1 承诺

| 能力 | v1 | 说明 |
|---|---|---|
| 插件内置网页（BDS 运行时） | 是 | LSE `HttpServer`；实时/历史查询；无冷查看 |
| 单独挂载网页端（可选） | 是，独立部署 | 离线查看的唯一来源；没有它就没有冷查看 |
| 在线玩家背包/装备/副手实时视图 | 是 | 主背包实时；副手/末影箱低频 |
| 物品**完整 NBT** 查看 | 是 | 小 NBT 内联；大 NBT 走 `nbtRef`；不静默截断 |
| 修改在线玩家背包/NBT | 是 | 动作 + 权限 + 审计 |
| 还原历史背包 | 是 | 在线/离线；pre-restore 备份 |
| 修改离线玩家（BDS 运行中） | 是 | `mc.getPlayerNbt`/`setPlayerNbtTags` + UUID 映射 |
| BDS 关闭时修改离线玩家 | 仅形态 B | 单独挂载网页端排队；开服后插件执行 |
| BDS 关闭时查看最后备份 | 仅形态 B | 没有单独网页端就完全不可用 |
| 每分钟一个备份桶 | 是 | 跨分钟边界在线每分钟一个；不补历史桶 |
| 网页指令执行 | 是 | 白名单/危险级别/确认/审计/限流 |
| 物品去向：丢弃/拾取归因 | 是 | 直接事件 + 槽位差 |
| 物品去向：合成推断 | 实验性 | 默认关闭；只对配方命中项标 `craft` |
| 模块 API（内置模块） | 是 | 只对 `command`/`logistics`；API 已缩小 |
| 操作记录链 | 是 | 单队列；服务端/插件代算哈希 |
| 外部多服/Redis/Mongo/Kafka/WS | 否，v2 | 见 [06](06-v2-外部模式与分布式.md) |
| 第三方模块 | 否 | v1 不开放 |
| 直接编辑世界存档（BDS 关闭时立即改） | 否 | 只排队；v2 再评估 |

### 2.2 硬边界

- 形态 A 不提供冷查看；BDS 停止后网页不可用。
- 形态 B 是可选的独立组件；未部署/未运行 = 没有离线查看，没有兜底。
- BDS 关闭时的离线修改只在形态 B 的队列里；不在网页端直接改世界存档。
- 完整 NBT 超限走 `nbtRef` 或拒绝，不静默截断。
- 不做外部多服/分布式/WS/多租户/第三方模块。

### 2.3 为什么这样切

- 用户明确：离线查看是单独挂载网页端的功能，没有就不可用；因此不能把“常驻服务”伪装成插件内置能力。
- 形态 A 保留“开箱即用”的实时查看；形态 B 解决“BDS 关了还能看”，但必须单独部署。
- 完整 NBT/离线修改都放在插件动作层；网页端只排队/展示，不直接写世界存档。
- 先验证 LSE 的 NBT/离线 NBT 能力与 HttpServer 阻塞行为，再冻结实现。

## 3. 运行时探针

### 3.1 探针清单

| 编号 | 问题 | 为什么决定架构 | 预计耗时 |
|---|---|---|---|
| A | 内置 `HttpServer` 回调是否阻塞 tick | 形态 A 的处理器能否同步查本地存储 | 1 天 |
| B | `onInventoryChange` 的真实语义 | 影子状态/分钟备份/物品去向准确性 | 1–2 天 |
| C | `KVDatabase.listKey()` 的实际开销 | 形态 A 的本地历史索引 | 0.5 天 |
| D | 令牌随机性 | 形态 A/B 的 Web 令牌生成 | 0.5 天 |
| E | 完整 NBT 的序列化成本与大小 | 内联/`nbtRef`/编辑上限 | 1 天 |
| F | 离线玩家 NBT 读写（`mc.getPlayerNbt`/`setPlayerNbtTags`） | 离线修改是否可行 | 1–2 天 |
| G | 单独挂载网页端：推送/冷查看/动作队列 | 离线查看与开服执行 | 1 天 |
| H | `webbundle-web` 静态资源 + 数据库并发 | 独立网页端是否稳定 | 0.5 天 |

B/F/G 是 v1 的核心；A 只影响形态 A；C/D 是降级/令牌；E/H 决定 NBT 与独立网页端的工程边界。

### 3.2 探针 A：内置 HttpServer 是否阻塞 tick

**做法**：

1. 最小 qjs 插件，启动 `HttpServer`。
2. 路由：`GET /fast` 直接返回；`GET /sync` 调 `httpGetSync` 到 200ms 慢服务；`GET /cpu` 忙等 200ms。
3. 用 `mc.listen("onTick")` 记录 tick 间隔；控制台/玩家观察卡顿。
4. 场景：空闲、每秒 1 个 `/sync`、每秒 10 个并发 `/sync`、每秒 1 个 `/cpu`。

**判定**：

- 通过：`/sync` 期间 tick p99 增加 ≤5ms；`/fast` 不被长时间阻塞。
- 失败：tick p99 增加 >50ms 或 `/fast` 阻塞 >1s → 形态 A 的 HTTP 处理器只读内存，禁止同步查存储；历史查询改异步/只读缓存。

### 3.3 探针 B：onInventoryChange 语义

记录每个事件 `ts/tick/player/slot/old/new`，测试：give（单个/连续）、clear、工作台合成、潜影盒、丢弃/拾取、副手、盔甲、死亡、漏斗。

判定：

- 通过：主背包逐槽可追踪；副手/盔甲有可预测补充；最终状态可由事件 + 对账还原。
- 失败：批量合并/漏槽/顺序错乱 → 加容器关闭/分钟边界对账；合成默认关闭。

### 3.4 探针 C：listKey 开销

1 万/10 万/100 万键，测 `listKey()` 与内存；启动调用一次。

判定：10 万 <500ms、100 万 <5s 通过；否则形态 A 不建全量索引，用分块/短保留。

### 3.5 探针 D：令牌随机性

- 形态 A：qjs 无 `crypto`；用 `system.randomUuid()` ×2，检查 version/variant/重复率/熵。
- 形态 B：独立网页端用 OS CSPRNG。
- 判定不通过则用外部熵源；禁止 `Math.random()`。

### 3.6 探针 E：完整 NBT 成本

构造普通/附魔/命名/潜影盒/书等 100 个物品，测 `item.getNbt().toSNBT()`、`NBT.parseSNBT` + `setNbt` 往返、备份总大小；测 >64KB/>512KB 行为。

判定：普通背包序列化 p99 ≤5ms、解析 p99 ≤10ms 通过；否则小内联/大 ref/按需刷新/设上限。

### 3.7 探针 F：离线玩家 NBT 读写

测试账号进服/退服 → `data.xuid2uuid` → `mc.getPlayerNbt` → 改 `Inventory/Armor/Offhand/EnderChestInventory` → `mc.setPlayerNbtTags` → 再读校验 → 玩家进服验证；测试写入期间玩家进服的冲突。

判定：能读能改能校验、冲突可检测通过；否则离线修改排队到玩家在线，或限制为只读。

### 3.8 探针 G：单独挂载网页端

1. 启动插件内置网页（形态 A）与 `webbundle-web`（形态 B）。
2. 插件推送备份/事件到 B；B 停止/重启，校验补写。
3. 停止 BDS：B 仍可看最后备份/备份/NBT/物品去向，`dataAsOf` 正确。
4. **不启动 B**：确认 BDS 停止后没有任何网页可用（符合需求边界）。
5. BDS 停止时通过 B 提交离线修改，状态 `queued_offline`；启动 BDS，插件拉取并执行。
6. 杀 B：插件 spool；重启补写；形态 A 不受影响。

判定：通过 = 离线查看只在 B 存在时可用；队列/执行/补写正确。失败 = 队列丢失/重复/冷查看读到半写数据。

### 3.9 探针 H：webbundle-web 静态资源 + 数据库并发

20 并发 1MB 静态资源 + 20 并发写入；网页长查询与写入并发；checkpoint 恢复。

判定：字节完整、并发不崩、p95 可接受；否则静态交给反向代理/拆进程。

## 4. 探针工程

```
plugins/WebBundleProbe/
├── manifest.json
├── index.js
├── probe-a-http.js
├── probe-b-inventory.js
├── probe-c-kv.js
├── probe-e-nbt.js
├── probe-f-offline-nbt.js
├── probe-g-external.js
└── tools/
    ├── fake-web.mjs
    └── analyze.py
```

原则：

- 探针与正式插件分开，不进入发布包。
- JSON lines 输出；测试账号/测试存档；不碰生产数据。
- 结论写回本文与 01 §3。

## 5. 决策树

```
A 通过？
├─ 是：形态 A 可同步读本地缓存；历史查询限 200ms
└─ 否：形态 A 只读内存；历史改异步/预聚合

B 通过？
├─ 是：影子状态 + 事件归因；合成实验性
└─ 否：对账；合成关闭；物品去向只承诺丢弃/拾取

C 通过？
├─ 是：形态 A 可建启动索引
└─ 否：分块/短保留，或不提供深历史

D 通过？
├─ 是：qjs/服务生成令牌
└─ 否：外部熵源

E 通过？
├─ 是：小 NBT 内联，大 NBT ref
└─ 否：全部 ref/按需刷新；设上限

F 通过？
├─ 是：离线修改走 setPlayerNbtTags
└─ 否：离线修改排队到玩家在线/只读

G 通过？
├─ 是：形态 B 提供冷查看/队列
└─ 否：B 不可用；形态 A 仍可用，但**没有离线查看**（符合边界）

H 通过？
├─ 是：静态+DB 同进程
└─ 否：静态交给反向代理/拆进程
```

任何一项失败，先改设计再进 M1。
